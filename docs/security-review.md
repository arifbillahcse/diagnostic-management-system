# Security review

Status: Phase 5. A review of the code by its author, with tests where a
finding could be tested. It is not an independent penetration test, and it
does not cover the server the system will run on. Both are still needed
before real patient data is entered.

## What was checked

| Area | Finding | State |
|---|---|---|
| **Clinic isolation** | Each clinic has its own database and its own MySQL user. The clinic connection is unusable until a clinic is resolved from the request's domain. Queued jobs reconnect to the clinic they were created for | Tested |
| **Session reuse across clinics** | User IDs repeat between clinic databases, so a session cookie copied to another clinic's address could sign in as someone else. The clinic is stored in the session at login and checked on every request | Tested |
| **Access control** | Every action class checks a permission before it does anything. Screens hide what a user cannot do, and Filament refuses to run a hidden action. A disabled module's permissions are always denied | Tested per action and per screen |
| **Branch scope** | Permissions can be limited to a branch and actions pass the record's branch. Lists are not yet filtered by branch | Open, see below |
| **Guessable addresses** | Links use a random public ID, never the row number. A row number in an address answers "not found" | Tested |
| **Passwords** | Hashed with Laravel's default. Minimum 10 characters. Never written to the audit trail or the data export | Tested |
| **Own account** | A user can change only their own password, and must give the current one. Name, email, and roles need the user-management permission | Tested, including a crafted request |
| **Two-step sign-in** | Optional per user, with an authenticator app and recovery codes. The secret is stored encrypted | Tested. Not enforced for any role, see below |
| **Login attempts** | Filament limits repeated attempts. Failed and successful sign-ins are audited. A deactivated user is signed out on their next request | Tested |
| **Audit trail** | Append-only in the application, and on MySQL the database refuses UPDATE and DELETE on it | Tested on MySQL |
| **Money and result history** | Invoice lines, payments, account entries, commission entries, and verified result versions are append-only in the application and protected the same way in the database | Tested on MySQL |
| **SQL injection** | All queries use bound parameters. The few places that build SQL by hand (creating a clinic database and user, backup, hardening triggers) accept only names matching a strict pattern | Reviewed |
| **Cross-site scripting** | Blade escapes all output. The four places that print unescaped HTML print either escaped text with line breaks or a barcode generated by the server | Reviewed, and tested on the lab report |
| **Request forgery** | Screens go through Filament and Livewire, which check a token. The print and export addresses only read data | Reviewed |
| **Uploads** | Logo and signature only: PNG or JPEG, size limited, stored on a private disk with no web address. A document embeds a file only from the current clinic's own folder | Tested, including another clinic's file |
| **PDF generation** | Remote files, embedded PHP, and JavaScript are switched off in the PDF engine | Reviewed |
| **Data export** | Needs its own permission. Passwords and two-step secrets are left out. Text a spreadsheet would run as a formula is made harmless. Every download is audited. The zip is deleted after sending | Tested |
| **Browser caching** | Every page is sent with "no-store", so a shared reception PC does not show patient pages from the Back button after sign-out | Tested |
| **Other headers** | Framing by other sites is refused; content-type sniffing is off; HTTPS is pinned once the site is served over HTTPS | Tested |
| **Secrets in settings** | Settings can be stored encrypted and are redacted in the audit trail. Clinic database passwords are stored encrypted | Tested |
| **Backups** | Compressed, optionally encrypted, readable only by the owner of the file, and proven by a trial restore | Tested on MySQL |
| **Dependencies** | `composer audit` reports no known vulnerabilities, and runs in the test pipeline | Checked |
| **Production settings** | `php artisan platform:doctor` checks debug mode, HTTPS, cookie settings, strict SQL mode, queue, and backup settings | Tested |

## Fixed during this review

| Problem | Fix |
|---|---|
| Pages could be kept in the browser cache | "no-store" on every response |
| No security headers | Added by one middleware |
| A user could not change their own password | "My account" page |
| No second sign-in step was available | Authenticator app support |
| The audit log relied on the application alone | Database triggers on MySQL |
| A failed `mysqldump` in the middle of a pipeline could have been saved as a good backup | The pipeline now fails as a whole, and every backup is checked by a trial restore |

## Open, in order of importance

1. **Server hardening is not part of the code.** HTTPS certificates, the
   firewall, operating system updates, MySQL not reachable from the internet,
   and file permissions are the hosting side's job. `platform:doctor` checks
   only the application's own settings.
2. **Two-step sign-in is optional for everyone.** Recommended next step:
   require it for the Owner and Admin roles. It needs a decision, because it
   also needs a recovery path when an owner loses their phone.
3. **The database protection stops accidents and injected queries, not an
   insider.** The clinic's MySQL user could remove the triggers. Tightening
   this means running migrations as a different MySQL user from the one the
   application uses day to day.
4. **Lists are not filtered by branch.** Harmless with one branch. It must be
   done with the multi-branch module (Phase 11).
5. **No content security policy.** Filament and Livewire rely on inline
   scripts, so a strict policy needs nonces throughout. All output is escaped,
   which is the main defence.
6. **Passwords are not checked against lists of leaked passwords.** That
   check sends part of a password hash to an outside service; it is left off
   until that is a deliberate choice.
7. **Platform staff access.** There is no support screen yet, so support
   today means database access. The logged, owner-visible support session in
   `permissions.md` is still to be built.
8. **Uploaded files are not in the database backup.** They are few (a logo,
   signatures) and must be copied separately from
   `storage/app/private/clinics`.
9. **The LGPL libraries and the customer terms** still need the lawyer's
   review, as does how patient data may be stored and for how long.

## Before real patient data

- [ ] `php artisan platform:doctor` passes on the production server
- [ ] The site is reachable over HTTPS only
- [ ] MySQL accepts connections only from the application server
- [ ] `BACKUP_PATH` and `BACKUP_PASSPHRASE` are set, the nightly backup has
      run, and its folder is copied to another place
- [ ] One backup has been restored by hand on a different machine
- [ ] The application key and the backup passphrase are stored somewhere
      other than the server
- [ ] Owners have switched on two-step sign-in
- [ ] A lawyer has reviewed the customer terms and data handling
- [ ] Someone other than the author has tested the system for security
